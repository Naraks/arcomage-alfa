# Инструкции для агента (Claude) в этом репозитории

Этот файл — заметки для себя (агента), не для человека-разработчика: как вести себя в репозитории `alfa`
между сессиями, раз контекст каждый раз стирается. Человеческий git-процесс уже полностью описан в
`CONTRIBUTING.md` — этот файл его не дублирует, а фиксирует то, что либо не вошло туда явно, либо
расходится с тем, как реально ведёт себя агент в текущей песочнице.

## Откуда брать "что делать дальше"

`docs/dev_plan_tickets.md` — источник правды по бэклогу. Тикеты `ARC-XXX`, у каждого — критерии приёмки
чекбоксами. Открытый (невыполненный) тикет — незакрытый чекбокс `- [ ]`. Порядок работы обычно определяют
**зависимости и приоритет**, а не порядковый номер ARC-ID (в git log соседние коммиты вполне могут быть
`ARC-039` → `ARC-042` → `ARC-041`, если 040 заблокирован незакрытой зависимостью). Если тикет явно
отложен с пометкой "делать после ARC-YYY" (см., например, комментарий в `ui/deck/deck_screen.gd` про
ARC-046, ждавший ARC-038) — как только ARC-YYY закрыт, отложенный тикет становится следующим кандидатом.

## Что происходит по завершении тикета

1. Реализация + тесты (GUT, `tests/test_*.gd`) в одном или нескольких коммитах `ARC-XXX: ...`
   (формат — см. "Формат сообщений коммитов" в `CONTRIBUTING.md`).
2. В `docs/dev_plan_tickets.md`: чекбоксы критериев приёмки тикета — `[x]`, под ними блокквот
   `> ✅ Реализовано и проверено: ...` с тем, что сделано, какие отклонения от буквального текста тикета
   и почему, какие смежные баги попутно найдены/починены. Это тоже часть коммита.
3. **Закрытие GitHub Issue** — по `CONTRIBUTING.md`, при переходе тикета в `✅ Реализовано и проверено`
   обязательно закрыть привязанный issue:
   `gh issue close <номер> --repo Naraks/arcomage-alfa --comment "<итоговый статус>"`.
   Номер issue — в самом тикете, строка `**GitHub Issue:** [#N](...)`.
   **На практике в песочнице агента `gh` CLI и доступ к `github.com` обычно недоступны** (сеть
   заблокирована allowlist'ом) — это НЕ повод пропустить шаг молча. Если `gh`/сеть недоступны: явно
   написать об этом в финальном ответе пользователю и оставить закрытие issue как невыполненный пункт,
   а не притворяться, что он выполнен.
4. Многие тикеты в истории закрываются **двумя** коммитами: сначала реализация (`ARC-XXX: ...`), потом
   отдельный `ARC-XXX: confirm and close` — это финальное подтверждение обычно означает, что человек
   вручную прогнал игру/тесты в редакторе Godot и подтвердил, что всё работает. Агент не должен сам
   писать "confirm and close" коммит, если сам не смог прогнать тесты (см. ниже про ограничения
   песочницы) — это вводит в заблуждение относительно того, что реально проверено.

## Что коммитится прямо в `main`

`CONTRIBUTING.md` формально описывает trunk-based модель с короткоживущими ветками
`feature/ARC-XXX-...`, сливаемыми через PR, и защиту `main` от прямого пуша. **Фактически же вся история
репозитория — линейная последовательность коммитов прямо в `main`** (`git log` не содержит ни одного
merge-коммита): агент в этой песочнице клонирует `main`, коммитит туда напрямую (`git commit` без
создания `feature/...` веток) и такой коммит уже наблюдается запушенным на `origin/main` до начала
следующей сессии. Вывод: если явно не попросили иначе, агент должен коммитить сразу в `main`, а не
заводить feature-ветку — заведение ветки без последующего реального PR/мержа только создаст
расхождение с уже устоявшейся практикой репозитория.

Отдельно: пуш в `origin` из песочницы агента тоже обычно недоступен (тот же blocked-by-allowlist на
`github.com`) — коммит остаётся только локальным в рабочей копии песочницы. Это нужно явно проговаривать
пользователю, а не подразумевать, что изменения уже на GitHub.

## Ограничения песочницы, которые нужно проговаривать, а не замалчивать

- Нет бинарника Godot и нет сети до `github.com`/официальных зеркал, чтобы его скачать — GUT-тесты
  (`addons/gut/gut_cmdln.gd`) агент сам не прогоняет, только пишет их и проверяет вручную по аналогии с
  существующими тестами.
- Нет доступа к PyPI — `gdformat`/`gdlint` (`.pre-commit-config.yaml`, ARC-062) агент тоже не прогоняет.
- Нет `gh` CLI / доступа к GitHub API — issue не закрываются агентом автоматически (см. выше).
- Итог: после коммита обязательно писать пользователю, что именно не проверено (тесты/линт/пуш/issue) и
  что нужно сделать вручную (прогнать в редакторе, дождаться CI, запушить, закрыть issue).

## Прочие соглашения, которых агент придерживается по этому репозиторию

- Каждый экран — `Control` с логикой в `_ready() → _build_ui()`, тот же паттерн, что в
  `ui/shop/shop_screen.gd` и остальных `ui/*_screen.gd`. Разметка чаще строится кодом, а не в редакторе,
  кроме простой обёртки `.tscn` (корневой `Control` + `script =`).
- Тесты создают экземпляр экрана через `load(...).new()` или `preload(...).instantiate()` **без**
  добавления в дерево сцены, если тестируемый код не трогает `get_tree()`/`get_viewport()` в `_ready()`
  — так тестируются десятки существующих `test_*_screen.gd`.
- Тестовые данные (`PlayerData`/`CardData`/`ArtifactData`) — через `tests/fixtures.gd`
  (`TestFixtures`), не через `load()` реального контента из `data/cards/*.tres` (баланс карт часто
  меняется и не должен ломать тесты логики).
- Каждый `.gd`-файл начинается с блока `##`-комментариев: что это, зачем, ссылка на ARC-ID, и явные
  пометки о намеренных отклонениях/недоделанных смежных вещах — это уже сложившийся стиль документации
  прямо в коде, а не только в `docs/dev_plan_tickets.md`.
- Если по ходу тикета находится смежный баг — чинить его тут же и явно описывать в блокквоте тикета
  ("попутно нашёл и починил..."), а не заводить отдельный тикет, если это не крупная отдельная задача.
- Переиспользовать существующие сцены/экраны как под-сцены (`instance=ExtResource(...)`) вместо
  копирования их логики, если новый тикет объединяет уже реализованный функционал (пример — ARC-046).
