# Как мы работаем с репозиторием (Alfa)

Этот документ фиксирует Git-процесс проекта: ветвление, формат коммитов и связь работы с бэклогом
(`dev_plan_tickets.md`). Реализует тикет **ARC-060**. Более узкие правила (Git LFS, pre-commit хуки, шаблоны
PR/issue, защита ветки `main`) добавятся отдельными тикетами того же эпика (ARC-061–ARC-064) и дополнят этот
файл, не заменяя его.

## Модель веток

Проект использует **trunk-based** модель — она проще двухвeтковой (`main`+`develop`) и подходит соло-разработке
и маленькой команде:

* **`main`** — единственная долгоживущая ветка. Всегда в состоянии, которое можно собрать и запустить.
* **`feature/ARC-XXX-краткое-описание`** — короткоживущая ветка на один тикет из бэклога, например
  `feature/ARC-060-git-process` или `feature/ARC-002-battle-to-map`. Живёт, пока идёт работа над тикетом,
  сливается в `main` и удаляется сразу после мержа.
* Долгоживущей ветки `develop` **нет** — она добавляет накладные расходы на синхронизацию, которые не
  оправданы при нынешнем размере команды. Если команда вырастет и потребуется отдельная ветка стабилизации
  перед релизом — это отдельное решение, требующее пересмотра этого документа.
* Ветка на исправление багов после релиза называется так же, как и обычная фича: `feature/ARC-XXX-...`
  (баг тоже заводится как тикет с ARC-ID, отдельного префикса `fix/` не вводим, чтобы не плодить схемы
  именования).

## Формат сообщений коммитов

```
ARC-XXX: краткое описание в повелительном наклонении

(опционально) более подробное тело коммита — что и почему, а не как;
детали "как" видны из самого диффа.
```

Примеры:

```
ARC-060: добавить CONTRIBUTING.md с git-процессом
```

```
ARC-002: замкнуть переход из боя обратно на карту мира

Battle screen теперь читает MatchSettings.came_from_map и возвращает
на world_map_screen вместо бесконечного Restart, помечая узел
завершённым.
```

Правила:

* Заголовок коммита начинается с ID тикета (`ARC-XXX:`), даже если PR уже привязан к тикету через номер
  ветки/issue — так ID виден прямо в `git log` без перехода в трекер.
* Заголовок — в повелительном наклонении («добавить», «исправить», «убрать»), не в прошедшем времени
  («добавил») и не в виде существительного («добавление»).
* Один коммит — одно осмысленное изменение. Не нужно сжимать весь тикет в один коммит, если он естественно
  распадается на несколько шагов (например, отдельно тесты, отдельно реализация) — но каждый коммит всё равно
  получает тот же ARC-ID.
* Правки без своего тикета (опечатка, форматирование) помечаются `chore: краткое описание` — это единственное
  исключение из правила «каждый коммит ссылается на ARC-ID».

## Связь коммитов и PR с бэклогом

* Каждый коммит и каждый Pull Request должны ссылаться на тикет из `dev_plan_tickets.md` по его ID (`ARC-XXX`).
* Если работа не покрывается существующим тикетом — сначала добавить тикет в `dev_plan_tickets.md` (в
  подходящий эпик, с оценкой и критериями приёмки), потом начинать ветку. Это касается и небольших доработок:
  бэклог должен оставаться источником правды о том, что вообще делалось в проекте.
* Название ветки, заголовок PR и заголовки коммитов внутри него ссылаются на один и тот же ARC-ID — не должно
  быть PR, который тихо тянет за собой несколько несвязанных тикетов без явного указания каждого.
* Каждый тикет продублирован как GitHub Issue (ссылка — строка `**GitHub Issue:**` в самом тикете в
  `dev_plan_tickets.md`). При закрытии тикета в бэклоге (переход в статус `> ✅ Реализовано и
  проверено`) обязательно закрывать и соответствующий issue на GitHub —
  `gh issue close <номер> --repo Naraks/arcomage-alfa --comment "<итоговый статус>"` — бэклог и Issues
  не должны расходиться.

## Ревью (лёгкий процесс для маленькой команды)

Пока команда небольшая, полноценный процесс код-ревью с обязательным вторым ревьюером избыточен. Минимальный
набор перед мержем в `main`:

* Критерии приёмки тикета в `dev_plan_tickets.md` выполнены — отмечены галочками в самом тикете.
* Если тикет добавляет/меняет логику `match_manager.gd`/`artifact_manager.gd` — есть тест в
  `tests/test_*.gd` (GUT, см. ARC-072/073). Тестовые `PlayerData`/`CardData`/`ArtifactData` — через
  `TestFixtures` (`tests/fixtures.gd`, ARC-074), не через `load()`/`preload()` реального контента из
  `data/cards/*.tres` (тот часто меняется из-за баланса — Эпик C — и не должен ломать тесты логики).
* Тесты зелёные: `<путь до Godot.exe> --headless -s addons/gut/gut_cmdln.gd --path .`
* Ветка собирается и запускается локально хотя бы один раз перед мержем.

Когда появится CI (ARC-066), два последних пункта станут автоматической проверкой вместо ручной.

## Git LFS для бинарных ассетов

Реализует **ARC-061**. `.gitattributes` уже размечает бинарные типы ассетов (`*.png`, `*.jpg`, `*.wav`,
`*.ogg`, `*.mp3`, `*.ttf`, `*.otf` и т.п.) фильтром `filter=lfs diff=lfs merge=lfs -text`. Чтобы это
реально сработало, каждому, кто коммитит в репозиторий, нужно **один раз локально** поставить Git LFS:

* Windows: `winget install GitHub.GitLFS` или через установщик Git for Windows (там есть опция «Git LFS»),
  либо `scoop install git-lfs` / `choco install git-lfs`.
* После установки выполнить один раз в корне репозитория: `git lfs install`.

Без этого шага бинарные файлы, попадающие под правила `.gitattributes`, всё равно закоммитятся —
но обычными blob'ами в основную историю, а не через LFS, то есть само правило без установленного
клиента не защищает от раздувания репозитория.

На момент написания в истории репозитория бинарных ассетов нет (экспортные файлы вычищены в рамках
ARC-008), поэтому `git lfs migrate` по существующей истории не потребовался — правила покрывают будущие
коммиты. Если это изменится (например, при ручном добавлении крупного бинарника в обход правил), нужно
будет прогнать `git lfs migrate import --include="*.png,*.wav,..." --everything`.

> ✅ Реализовано и проверено: Git LFS установлен, `git lfs install` выполнен в репозитории. Тестовый
> `.png` закоммичен и `git show HEAD:test_lfs.png` показал текстовый LFS-pointer
> (`version https://git-lfs.github.com/spec/v1...`), а не бинарные байты.

## Pre-commit хуки и единый стиль GDScript

Реализует **ARC-062**. `.pre-commit-config.yaml` подключает `gdtoolkit` (`gdformat` — форматтер,
`gdlint` — линтер) как pre-commit хуки на все `.gd`-файлы. `.editorconfig` дополнен секцией `[*.gd]`
(`indent_style = tab`, `indent_size = 4`), чтобы IDE и форматтер были согласованы.

Установка (один раз локально, аналогично Git LFS в ARC-061):

```
pip3 install pre-commit "gdtoolkit==4.*"
pre-commit install
```

После этого `gdformat`/`gdlint` будут запускаться автоматически на изменённые `.gd`-файлы при каждом
`git commit`; коммит с ошибками линтера или неотформатированным кодом будет заблокирован (либо
`gdformat` перезапишет файл, и его нужно будет добавить в коммит повторно).

Разовый прогон по всей существующей кодовой базе (второй критерий приёмки ARC-062):

```
pre-commit run --all-files
```

Это должно дать «чистый» коммит без функциональных изменений — только форматирование.

> ✅ Реализовано и проверено: `pre-commit run --all-files` прогнан по всем 19 `.gd`-файлам. `gdformat`
> прошёл сразу, `gdlint` нашёл 17 замечаний (порядок `class_name`/`extends`, порядок `const`/`var`,
> один неиспользуемый аргумент) — все исправлены вручную и подтверждены повторным прогоном. Результат
> закоммичен отдельным коммитом `chore: прогнать gdformat по кодовой базе`.

## Шаблоны PR и issue

Реализует **ARC-063**. `.github/PULL_REQUEST_TEMPLATE.md` — чеклист для PR (привязка к `ARC-XXX`,
критерии приёмки, тесты, прогон в редакторе, `pre-commit`). `.github/ISSUE_TEMPLATE/bug_report.md` —
шаблон для багов из плейтестов (репро-шаги, окружение, связанный тикет); `config.yml` отключает
пустые issue без шаблона.

Репозиторий выложен на GitHub (`git@github.com:Naraks/arcomage-alfa.git`, remote `origin` уже
настроен). GitHub подхватывает эти шаблоны автоматически при создании PR/issue через веб-интерфейс —
отдельной настройки не требуется.

> ✅ Реализовано и проверено: репозиторий запушен на GitHub, New Issue в веб-интерфейсе подставляет
> заголовок и структуру `bug_report.md` автоматически.

## CI

Реализует **ARC-066**. `.github/workflows/ci.yml` — GitHub Actions workflow на каждый push и PR в
`main`:

1. Checkout с `lfs: true` (ARC-061).
2. Скачивание headless-бинарника Godot `4.7.1-stable` с официальных релизов (кэшируется между
   прогонами по `actions/cache`, чтобы не тянуть ~80 МБ каждый раз).
3. `--headless --editor --quit` — прогрев `.godot/` (импорт ассетов).
4. Прогон `addons/gut/gut_cmdln.gd` с `-gexit -gexit_on_success` — джоб падает, если хоть один тест
   красный (см. ARC-072/073). Отчёт экспортируется в JUnit XML и прикладывается как build artifact.

> ✅ Реализовано и проверено: первый прогон на GitHub Actions прошёл успешно (push в `main`).

## Защита ветки `main`

## Версия сборки и CHANGELOG

Реализует **ARC-069**. Версия — это git-тег вида `vX.Y.Z` (семвер). Тегов трогать вручную не нужно
для обычной разработки: они нужны только для релиза/плейтест-сборки с версией.

- Синглтон `BuildVersion` (`core/build_version.gd`) в рантайме читает `res://build_version.json` и
  показывает версию в главном меню (`ui/main_menu.tscn`, `VersionLabel`). В редакторе и локальных
  запусках файла нет — отображается `dev`.
- `.github/workflows/ci.yml` перед экспортом (джобы `export-web`, `build-windows-playtest`) пишет
  `build_version.json` из `git describe --tags --always --dirty --match 'v*.*.*'` и короткого SHA.
- `CHANGELOG.md` генерируется из истории коммитов по `cliff.toml` ([git-cliff](https://git-cliff.org/)),
  без Conventional Commits — группировка идёт по соглашению этого репозитория (`ARC-XXX: ...` /
  `chore: ...`, см. «Формат сообщений коммитов» выше).
- При пуше тега `vX.Y.Z` срабатывает `.github/workflows/release.yml`:
  - джоб `changelog-pr` прогоняет git-cliff и открывает PR с обновлённым `CHANGELOG.md` в `main` (не
    коммитит напрямую — ветка защищена, см. выше);
  - джоб `github-release` публикует GitHub Release с release-notes для этого тега.

Чтобы выпустить релиз: `git tag v0.2.0 && git push origin v0.2.0`, затем смержить открывшийся
авто-PR с CHANGELOG.md.

> ✅ Реализовано и проверено: прогон на реальном теге подтверждён — PR с CHANGELOG.md и GitHub Release
> создались, версия отображается в собранной игре.

## Публикация билд-артефактов

Реализует **ARC-070**. Две сборки, два способа получить их без локальной сборки в Godot:

- **Windows playtest-сборка** (`build-windows-playtest`, ARC-068) и **Web-сборка** (`export-web`,
  ARC-067) прикладываются к каждому прогону CI как artifact'ы (`alfa-windows-playtest`, `web-build`,
  `retention-days: 30`) — скачиваются со страницы прогона во вкладке Actions.
- **Web-сборка с `main` дополнительно публикуется на GitHub Pages** джобом `deploy-web-pages` (после
  `export-web`, только на push в `main`): `actions/upload-pages-artifact` + `actions/deploy-pages`.
  Открывается по прямой ссылке `https://naraks.github.io/arcomage-alfa/` в любом браузере, включая
  мобильный — не требует скачивания и распаковки.

Разовая настройка (сделать один раз в GitHub): Settings → Pages → Source → **GitHub Actions**. Без
этого джоб `deploy-web-pages` будет падать.

> ✅ Реализовано и проверено: источник Pages включён, деплой подтверждён рабочим.

## Уведомления о статусе CI

Реализует **ARC-071**. `.github/workflows/ci.yml` шлёт сообщение в Telegram через Bot API (`curl`,
без сторонних actions) в двух случаях:

- падает обязательная проверка (джоб `tests`) на push в `main`;
- успешно задеплоилась новая Web-сборка на GitHub Pages (см. выше) — сигнал, что можно идти играть.

Разовая настройка (нужно сделать один раз):
1. Создать бота через [@BotFather](https://t.me/BotFather) — `/newbot`, скопировать токен.
2. Узнать `chat_id`: написать боту в личку (или добавить в канал/группу), затем открыть
   `https://api.telegram.org/bot<TOKEN>/getUpdates` и найти `chat.id` в ответе.
3. В GitHub: Settings → Secrets and variables → Actions → New repository secret — добавить
   `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`.

Пока секреты не заведены, оба шага-уведомления тихо ничего не делают (не роняют джоб).

> ✅ Реализовано и проверено: секреты заведены как Repository secrets, уведомления подтверждены
> рабочими.

## Smoke-тест Web-сборки

Реализует **ARC-075**. Юнит-тесты (GUT) проверяют только логику внутри Godot и не ловят падения,
специфичные для WASM/браузера. `tools/web_smoke_test.mjs` открывает реальный экспортированный
`web/index.html` headless Chromium'ом через Playwright и падает при любой ошибке в консоли браузера
(JS-исключение, WASM-крэш, неудавшийся запрос) или если `<canvas>` не отрисовался. Джоб
`smoke-test-web` в `ci.yml` гоняет это на каждый push/PR после `export-web`.

Локальный запуск (после ручного `--export-release "Web" ./web/index.html`):
```
npm install --no-save playwright
npx playwright install --with-deps chromium
node tools/web_smoke_test.mjs web 8060
```

> ✅ Реализовано и проверено: с первого прогона поймал настоящий баг в `core/yandex_sdk.gd`
> (`has_method()` на `JavaScriptObject`, падал с `TypeError` в консоли браузера) — пофикшено, прогон
> зелёный.

## Отчёт о покрытии тестами

Реализует **ARC-077**. Настоящего line-coverage инструмента для GDScript/GUT нет — `tools/coverage_report.py`
даёт эвристику: для каждой функции в `core/*.gd` и AI-стратегиях (`data/resources/*ai_strategy*.gd`)
проверяет, упоминается ли её имя хоть в одном `tests/*.gd`. Не гарантирует, что тело функции реально
выполнилось (это не line coverage), но показывает, какие функции ядра вообще не всплывают в тестах —
на момент внедрения, например, AI-стратегии не упомянуты вообще.

Локальный запуск: `python3 tools/coverage_report.py` (пишет `coverage_report.txt`, только `python3`,
Godot не нужен). Джоб `coverage-report` в `ci.yml` прикладывает файл как artifact на каждый push/PR.

> ⚠️ Частично реализовано: код готов и прогнан локально, реальный прогон в CI не проверен из песочницы.
