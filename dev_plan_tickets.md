# Alfa (Arcomage Roguelike) — план разработки в виде тикетов

Документ подготовлен на основе аудита текущего кода проекта `C:\GodotProjects\alfa` (Godot 4.7) и существующих
файлов планирования (`cards_list.md`, `checklist.md`). Часть пунктов в `checklist.md` устарела —
ниже это учтено и исправлено фактическим состоянием кода.

Тикеты пронумерованы сквозным ID `ARC-XXX`; порядок эпиков в документе соответствует рекомендуемому порядку
выполнения — **Эпик J (репозиторий/CI/CD/автотесты) идёт первым**, поэтому его ID (ARC-060…ARC-077) выше, чем у
идущих следом эпиков A–I: нумерация отражает историю добавления тикетов в бэклог, а не порядок работы. Каждый
тикет — это готовая карточка для Jira/Trello/Linear: тип, приоритет, оценка, зависимости, описание, технические
детали (с указанием конкретных файлов) и критерии приёмки.

## 0. Аудит текущего состояния (важно прочитать перед стартом)

Фактически в проекте уже реализовано заметно больше, чем показывает `checklist.md`:

* **Ядро боя работает.** `core/match_manager.gd` содержит полноценный FSM (`START_MATCH → PLAYER_TURN/AI_TURN →
  PROCESS_CARD → CHECK_WIN → END_MATCH`), интерпретатор эффектов (`damage`, `direct_damage`, `build_wall`,
  `build_tower`, `mod_quarry/magic/dungeon`, `build`), обработку урона через стену, авто-сброс карты у ИИ в
  патовой ситуации и условия победы (высота башни, обнуление HP, накопление 300 ресурсов).
* **34 карты** уже созданы как `.tres` (`brick_1..11`, `gem_1..11`, `beast_1..10`, `wall_card`, `knight_card`) —
  это близко к нижней границе плана «30–60 карт», но `cards_list.md` не описывает `brick_11` и `gem_11` (документ
  устарел).
* **Два ИИ-профиля** (`default_ai_strategy.gd`, `aggressive_ai_strategy.gd`) с весовой системой оценки карт —
  реализованы, профили «Строитель» и «Маг/Экономист» — ещё нет.
* **Артефакты**: система есть (`artifact_manager.gd`), но реализован только 1 артефакт из 6 задуманных
  (`Кирка Гнома`), и триггеры ограничены `card_played`/`turn_started` — триггера `on_damage_taken` (нужен для
  «Шипастой Стены») нет вообще.
* **Карта мира**: есть только зачаточный вариант — 2 жёстко закодированных узла в `main_menu.gd`, работает только
  тип узла `BATTLE`. Генератора путей, узлов `SHOP`/`REST`/`EVENT`, экрана награды после боя — не существует.
* **Найдены конкретные баги** (см. Эпик A) — самый критичный: `ProfileManager` не зарегистрирован как autoload в
  `project.godot`, из-за чего бонусы мета-прогрессии в `match_manager.gd:30` никогда не применяются.
* **Экспорт под веб отсутствует.** `export_presets.cfg` содержит только пресет `Windows Desktop`. Ни одного
  HTML5-пресета для Яндекс Игр нет, хотя вся игра задумана как веб-игра.
* Меню/экраны сделаны как заглушки с `print(...)` вместо логики (Продолжить, Колода).

Рекомендация: вести работу по бэклогу ниже — он синхронизирован с реальным кодом.

## Эпик J — Репозиторий, CI/CD и автоматизация тестирования

Сейчас репозиторий — это рабочая копия без зафиксированного процесса (нет веток/ревью, в корне лежат
экспортированные бинарники по ~100 МБ, тесты — один самописный скрипт без фреймворка, CI отсутствует). Этот
эпик стоит начинать параллельно с Эпиком A, а не в конце проекта — чем раньше появится защита от регрессий,
тем дешевле обходятся баги в контенте и балансе (Эпики B–E).

#### ARC-061 — Настроить Git LFS для бинарных ассетов
- **Тип:** Task · **Приоритет:** Medium · **Оценка:** 2 SP · **Зависит от:** ARC-008
- **GitHub Issue:** [#3](https://github.com/Naraks/arcomage-alfa/issues/3)

- Прогнать `git lfs migrate` для уже закоммиченных крупных бинарников, если они есть в истории.

**Критерии приёмки:**
- [x] Новые бинарные ассеты автоматически уходят в LFS.
- [x] Размер обычной git-истории (без LFS) не растёт от добавления арта.

> ✅ Реализовано: `.gitattributes` расширен LFS-правилами, `git lfs install` выполнен в репозитории,
> инструкция — в `CONTRIBUTING.md`. Проверено вручную: тестовый `.png` закоммичен как LFS-pointer
> (`version https://git-lfs.github.com/spec/v1...`), а не бинарными байтами.

- **GitHub Issue:** [#20](https://github.com/Naraks/arcomage-alfa/issues/20)

**Описание:** `match_manager.gd:30` вызывает `get_node_or_null("/root/ProfileManager")`, ожидая synglton, но в
`project.godot` секция `[autoload]` содержит только `YandexSDK`, `GameEvents`, `MatchManager`, `MatchSettings`.
В результате бонусы мета-прогрессии (`tower_hp_bonus`, `resource_gain_bonus`) никогда не применяются — молча,
без ошибки.

**Критерии приёмки:**
- [x] `ProfileManager="*res://core/profile_manager.gd"` добавлен в `[autoload]`.
- [x] В `setup_match()` подтверждено логом/тестом, что бонусы реально прибавляются к `tower_hp`/`quarry`.
- [x] Написан unit-тест на применение бонуса (см. ARC-053).

> ✅ Реализовано и проверено: `ProfileManager` добавлен в `[autoload]` в `project.godot`. По пути снял
> `class_name ProfileManager` с `core/profile_manager.gd` — иначе тот же конфликт «class_name
> совпадает с именем автозагрузки», что уже чинили в `core/build_version.gd` (ARC-069): движок ронял бы
> скрипт с «hides an autoload singleton». Заодно нашёл и починил второй баг, который маскировался

> `null` (автозагрузки не было). Убрал лишнюю проверку — `profile` это обычное поле с дефолтным
> значением, всегда существует. Добавлен тест `test_setup_match_applies_profile_manager_bonuses` в
> `tests/test_match_manager.gd`, сверяет реальные значения бонусов из `ProfileManager.profile.player_stats`,

> матче.

### ARC-078 — Баг: ход не возвращается игроку после хода ИИ

**Описание:** В реальной игре (переход с карты мира в бой) матч навсегда зависал в состоянии `AI_TURN`

выходил без `end_turn()`.

  если она не задана (единая точка входа для всех боевых сценариев).
- `core/match_manager.gd` `execute_ai_turn()` — та же подстраховка на случай вызова в обход
  `setup_match()`; ветка с пустой рукой ИИ теперь тоже вызывает `end_turn()`.

**Критерии приёмки:**
- [x] После хода игрока ИИ либо играет карту, либо сбрасывает карту, либо (пустая рука) просто

- [x] Тест на `execute_ai_turn()` с `ai_strategy == null`.
- [x] Тест на `execute_ai_turn()` с пустой рукой ИИ.

> ✅ Реализовано и проверено: `tests/test_match_manager.gd` — 3 новых теста в разделе `setup_match /

## Рекомендуемая последовательность по фазам

| Фаза | Эпики | Фокус |
| :--- | :--- | :--- |
| **Фаза 0 (1 неделя)** | A, J (базовая часть: ARC-060, 061, 065, 066, 072, 073) | Починить критические баги, настроить веб-экспорт, поднять Git-процесс, CI и тест-фреймворк — без этого любая последующая работа не защищена от регрессий. |

Итого ориентировочно 9–11 недель — совпадает с изначальной оценкой, но теперь основано на
реальном состоянии кода, а не на предположении «всё с нуля». Эпик J намеренно растянут по всем фазам: базовая
часть (репозиторий, CI, тест-фреймворк) нужна с первого дня, а более продвинутые вещи (авто-версионирование,
smoke-тесты билда) можно достраивать по мере готовности остального функционала.

## Как использовать этот бэклог

1. Перенести все тикеты (`ARC-001…ARC-059` и `ARC-060…ARC-077`) в вашу таск-систему (Jira/Trello/Linear/GitHub
   Issues) как есть — поля уже готовы под стандартные колонки (Тип, Приоритет, Оценка, Зависимости).
2. Использовать `checklist.md` только как краткий чек-лист «готово / не готово» верхнего уровня, обновляя его по
   мере закрытия тикетов — сам список пунктов в нём стоит сверить с этим документом (там уже есть
   расхождения, отмеченные в разделе 0).
