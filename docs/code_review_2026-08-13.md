# Код-ревью кодовой базы (2026-08-13)

Ревью выполнено агентом по `core/`, `entities/`, `data/`, `ui/`, `tests/`, `tools/` и конфигурации проекта
(`project.godot`, CI, `.gdlintrc`, `.pre-commit-config.yaml`). Код не менялся — документ фиксирует
замечания и предложения на будущее.

## Баги и риски

### core/

- `entities/card/card.gd:38-45` — `_gui_input` обращается к `card_data.card_name` без null-проверки,
  хотя в соседнем `_on_mouse_entered` (строка 74) такая проверка есть.
- ~~`core/profile_manager.gd:201-221` — ошибки записи (`FileAccess.open` → `null`) и ошибки парсинга JSON
  при загрузке профиля проглатываются без единого лога — при повреждённом сохранении игрок тихо теряет
  прогресс без объяснения.~~ **Исправлено.** `save_profile()`/`load_profile()` теперь логируют
  `push_error` при неудачном открытии файла (с кодом `FileAccess.get_open_error()`), при ошибке разбора
  JSON (со строкой и сообщением `JSON.get_error_line()`/`get_error_message()`) и при повреждённом
  формате (когда `json.data` — не `Dictionary`); во всех этих случаях `profile` не перезаписывается, а
  функция выходит раньше, не трогая уже загруженный профиль в памяти.
- ~~Ни в `ProfileManager`, ни в `RunSaveData` нет поля версии сохранения — при будущем изменении
  структуры не на чем строить миграцию/обратную совместимость.~~ **Исправлено.** Добавлены
  `ProfileManager.SAVE_VERSION`/`profile["save_version"]` и `RunSaveData.CURRENT_VERSION`/
  `@export var save_version`. `RunSaveManager.load_run()` сравнивает версию загруженного сохранения с
  текущей и выдаёт `push_warning` при расхождении — сама миграция данных между версиями не
  реализовывалась (версия пока единственная), но теперь есть на чём её строить. Для `ProfileManager`
  аналогичная проверка версии в `load_profile()` не добавлялась — её формат исторически терпим к
  недостающим ключам (`profile.get(key, default)` везде), так что для профиля миграция менее критична;
  если понадобится строгая миграция и там, `SAVE_VERSION` уже на месте.

### ui/

- `ui/event/event_screen.gd:17-18` — `load(_pick_random_event_path())` не проверяется на `null` перед
  использованием в `_build_ui()`.
- `ui/reward/reward_screen.gd:56-90` — слоты наград индексируют массив карт без проверки размера
  относительно числа слотов — потенциальный `Array index out of bounds`, если каталог карт окажется
  урезан.
- `ui/battle/battle_screen.gd:347-372` — во время 0.3с анимации клика по карте блокируется только сама
  нажатая карта, но не весь `hand_container` — можно успеть кликнуть вторую карту и запустить
  параллельный `play_card_by_index`.
- `ui/shop/shop_screen.gd:14` — `_transaction_in_progress` не защищает ни от чего: код синхронный,
  гонка физически невозможна, флаг просто вводит в заблуждение при чтении.
- `ui/deck/deck_screen.gd:69-75` — `_load_deck_to_show()` выглядит как геттер, но имеет побочный эффект
  (перезаписывает `MatchSettings.*` через `RunSaveManager.load_run()`), вызывается безусловно даже когда
  экран встроен в профиль.
- Несогласованная защита `get_viewport_rect()` вне дерева сцены: в `settings_screen.gd` есть fallback, в
  `event_screen.gd`/`rest_screen.gd` — нет (пока не стреляет, т.к. эти экраны не тестируются через прямой
  вызов `_build_ui()` вне дерева, но это мина для следующего теста по аналогии).
