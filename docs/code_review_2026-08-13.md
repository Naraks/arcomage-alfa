# Код-ревью кодовой базы (2026-08-13)

Ревью выполнено агентом по `core/`, `entities/`, `data/`, `ui/`, `tests/`, `tools/` и конфигурации проекта
(`project.godot`, CI, `.gdlintrc`, `.pre-commit-config.yaml`). Код не менялся — документ фиксирует
замечания и предложения на будущее.

## Баги и риски

### core/

- `entities/card/card.gd:38-45` — `_gui_input` обращается к `card_data.card_name` без null-проверки,
  хотя в соседнем `_on_mouse_entered` (строка 74) такая проверка есть.

### ui/

- ~~`ui/event/event_screen.gd:17-18` — `load(_pick_random_event_path())` не проверяется на `null` перед
  использованием в `_build_ui()`.~~ **Исправлено.** `_ready()` проверяет результат `load(...)` и при
  `null` делает `push_error` и уходит на карту через `_return_to_map()` вместо падения в `_build_ui()` на
  `_event.event_title`.
- ~~`ui/reward/reward_screen.gd:56-90` — слоты наград индексируют массив карт без проверки размера
  относительно числа слотов — потенциальный `Array index out of bounds`, если каталог карт окажется
  урезан.~~ **Исправлено.** `_build_battle_slots()`/`_build_elite_slots()`/`_build_boss_slots()` больше не
  индексируют `paths[i]`/`common_paths[0..1]` вслепую: количество карточных слотов ограничено
  `mini(N, paths.size())`, а «гарантированный» редкий слот в элитной награде теперь вычисляет индекс
  замены (`replace_index`) относительно фактического числа обычных слотов, а не жёстко зашитой двойки. При
  здоровом каталоге карт (как сейчас) поведение и тесты не меняются — деградация плавная, а не падение.
- ~~`ui/battle/battle_screen.gd:347-372` — во время 0.3с анимации клика по карте блокируется только сама
  нажатая карта, но не весь `hand_container` — можно успеть кликнуть вторую карту и запустить
  параллельный `play_card_by_index`.~~ **Исправлено.** Добавлен флаг экрана `_card_play_in_progress`:
  пока идёт анимация розыгрыша одной карты, и левый клик (розыгрыш), и правый клик (сброс) по любой
  карте руки игнорируются. Сброс во время анимации розыгрыша дополнительно защитил тем же флагом — тот
  же корень проблемы (async-анимация не блокирует остальные взаимодействия с рукой), не только исходно
  описанный сценарий двойного клика на розыгрыш.
- ~~`ui/shop/shop_screen.gd:14` — `_transaction_in_progress` не защищает ни от чего: код синхронный,
  гонка физически невозможна, флаг просто вводит в заблуждение при чтении.~~ **Исправлено.** Флаг и все
  его проверки/присвоения удалены из `_try_buy_card`/`_request_removal`/`_confirm_removal` — код был и
  остаётся синхронным, гонка невозможна. Заодно удалён `tests/test_shop_screen.gd::
  test_input_during_transaction_cannot_purchase` — тест проверял только сам этот флаг, а не реальное
  поведение, и без флага потерял смысл.
- ~~`ui/deck/deck_screen.gd:69-75` — `_load_deck_to_show()` выглядит как геттер, но имеет побочный эффект
  (перезаписывает `MatchSettings.*` через `RunSaveManager.load_run()`), вызывается безусловно даже когда
  экран встроен в профиль.~~ **Исправлено.** Помимо переименования (`_resolve_deck_to_show` + `##`-
  комментарий, явно называющий побочный эффект), исправлен смежный баг серьёзнее стилистического: экран
  всегда встроен в профиль (`deck_screen.tscn` используется только внутри `profile_screen.tscn` с
  `embedded_in_profile = true`), поэтому `RunSaveManager.load_run()` вызывался безусловно при каждом
  открытии вкладки профиля — включая случаи посреди активного забега, перезаписывая
  `MatchSettings.run_deck`/`world_map_data`/... данными с диска. А сохранение (`RunSaveManager.save_run()`)
  вызывается только из `event_screen.gd` и `world_map_screen.gd` — покупки в магазине и бонусы отдыха на
  диск сразу не пишутся. Итог: просмотр профиля мог тихо откатить незасейвленные покупки/бонусы текущего
  забега. Теперь при наличии живого `MatchSettings.world_map_data` в памяти используется он напрямую, без
  обращения к диску; загрузка с диска остаётся только для случая, когда живого состояния ещё нет (открыли
  профиль сразу из главного меню, не продолжая забег).
- ~~Несогласованная защита `get_viewport_rect()` вне дерева сцены: в `settings_screen.gd` есть fallback, в
  `event_screen.gd`/`rest_screen.gd` — нет (пока не стреляет, т.к. эти экраны не тестируются через прямой
  вызов `_build_ui()` вне дерева, но это мина для следующего теста по аналогии).~~ **Исправлено.**
  `event_screen.gd`/`rest_screen.gd`::`_build_ui()` теперь считают `viewport_size` один раз в начале с тем
  же fallback-паттерном, что и `settings_screen.gd`
  (`get_viewport_rect().size if is_inside_tree() else Vector2(1280, 720)`), и переиспользуют его вместо
  повторных прямых вызовов `get_viewport_rect()`.
