# Alfa (Arcomage Roguelike) — план разработки в виде тикетов

Документ подготовлен на основе аудита текущего кода проекта `C:\GodotProjects\alfa` (Godot 4.7) и существующих
файлов планирования (`cards_list.md`, `checklist.md`). Часть пунктов в `checklist.md` устарела —
ниже это учтено и исправлено фактическим состоянием кода.

Тикеты пронумерованы сквозным ID `ARC-XXX`; порядок эпиков в документе соответствует рекомендуемому порядку
выполнения — **Эпик J (репозиторий/CI/CD/автотесты) идёт первым**, поэтому его ID (ARC-060…ARC-077) выше, чем у
идущих следом эпиков A–I: нумерация отражает историю добавления тикетов в бэклог, а не порядок работы. Каждый
тикет — это готовая карточка для Jira/Trello/Linear: тип, приоритет, оценка, зависимости, описание, технические
детали (с указанием конкретных файлов) и критерии приёмки.

  устарел).
* **Два ИИ-профиля** (`default_ai_strategy.gd`, `aggressive_ai_strategy.gd`) с весовой системой оценки карт —
  реализованы, профили «Строитель» и «Маг/Экономист» — ещё нет.
* **Артефакты**: система есть (`artifact_manager.gd`), но реализован только 1 артефакт из 6 задуманных
  (`Кирка Гнома`), и триггеры ограничены `card_played`/`turn_started` — триггера `on_damage_taken` (нужен для

#### ARC-061 — Настроить Git LFS для бинарных ассетов
- **Тип:** Task · **Приоритет:** Medium · **Оценка:** 2 SP · **Зависит от:** ARC-008
- **GitHub Issue:** [#3](https://github.com/Naraks/arcomage-alfa/issues/3)

**Описание:** По мере роста арт-контента (иконки карт из ARC-022, частицы из ARC-045, аудио) обычный git будет
раздувать историю. Уже сейчас в репозитории лежали случайные экспортные бинарники на ~100 МБ (ARC-008) —
признак того, что бинарные файлы не отделены от исходников политикой репозитория.

**Технические детали:**
- `.gitattributes` уже существует — расширить его правилами `*.png *.wav *.ogg *.ttf filter=lfs diff=lfs merge=lfs -text` и т.п.
- Прогнать `git lfs migrate` для уже закоммиченных крупных бинарников, если они есть в истории.

**Критерии приёмки:**
- [x] Новые бинарные ассеты автоматически уходят в LFS.
- [x] Размер обычной git-истории (без LFS) не растёт от добавления арта.

> ✅ Реализовано: `.gitattributes` расширен LFS-правилами, `git lfs install` выполнен в репозитории,
> инструкция — в `CONTRIBUTING.md`. Проверено вручную: тестовый `.png` закоммичен как LFS-pointer
> (`version https://git-lfs.github.com/spec/v1...`), а не бинарными байтами.
>
> **Смежный баг найден позже (при работе над ARC-044):** `pre-commit` у автора тикета на каждый коммит падал
> с `error: ...: patch does not apply` на файлах `addons/gut/fonts/*.ttf`/`addons/gut/gui/*.png`/
> `addons/gut/icon.png`/`addons/gut/images/*.png` — pre-commit перед прогоном хуков стэширует незакоммиченные
> изменения и потом накатывает их обратно патчем; патч не накатывался именно на эти файлы.
>
> Причина — проверено напрямую (`git cat-file -p` на blob'ы этих файлов в HEAD): это обычные Git-блобы с
> реальными magic bytes (`00 01 00 00` — sfnt/TTF, `89 50 4E 47` — PNG), а не LFS-pointer'ы, хотя
> `.gitattributes` требует для них `filter=lfs` уже с самого первого коммита репозитория. Файлы попали в
> историю в ARC-072 («установить и включить плагин GUT», коммит `6ab53f6`) — эта сессия агента шла в
> песочнице **без установленного `git-lfs`** (`git lfs version` → `'lfs' is not a git command`), поэтому
> `filter=lfs` в `.gitattributes` молча не сработал и `git commit` записал файлы как обычные блобы вместо
> LFS-pointer'ов — Git не считает это ошибкой, если filter-driver не зарегистрирован, а просто пропускает
> фильтрацию.
>
> На машине, где `git-lfs` реально установлен (у автора тикета), `git status`/`git diff`/`git add` каждый раз
> прогоняют "clean"-фильтр LFS по этим файлам для сравнения с индексом — результат (LFS-pointer) физически не
> может совпасть с уже закоммиченным обычным блобом, поэтому эти файлы **навсегда** выглядят "изменёнными",
> что бы в них ни лежало. Отсюда и падение `pre-commit`.
>
> **Исправление (не выполнено агентом — требует `git-lfs`, недоступного в песочнице, см. `CLAUDE.md`):**
> ```
> git add --renormalize .
> git commit --no-verify -m "chore: ARC-061 — перегнать addons/gut/* через LFS-фильтр (ARC-072 закоммитил их как обычные блобы)"
> ```
> `--renormalize` не переписывает историю (в отличие от `git lfs migrate import --everything`, который тоже
> решил бы проблему, но задним числом меняет хеши всех коммитов, задевающих эти файлы, и требует
> `push --force`) — просто один обычный коммит, где эти файлы наконец конвертируются в LFS-pointer'ы. После
> него `git status` на файлах `addons/gut/*` должен стать пустым при отсутствии реальных правок.

### ARC-083 — Баг: smoke-test-web падает из-за Yandex SDK вне iframe

- **Тип:** Bug · **Приоритет:** Critical · **Оценка:** 1 SP

**Описание:** После восстановления Yandex SDK-скрипта в `export_presets.cfg` (ARC-080) прогон
`node tools/web_smoke_test.mjs` (тот же механизм, что CI-джоб `smoke-test-web`, ARC-075) стал падать —
12 `[pageerror] No parent to post message`. Причина: `YaGames.init()` внутри себя общается с родительским
окном через `postMessage` — это работает только когда страница реально встроена в iframe платформы Yandex
Games. При локальном запуске (`python -m http.server`), в CI-смоук-тесте и на GitHub Pages (ARC-070/071,
страница открывается напрямую, не через Yandex) родителя нет, и SDK кидает эту ошибку раз за разом —
`web_smoke_test.mjs` валит тест на любой `pageerror`.

**Критерии приёмки:**
- [x] Скрипт SDK (`https://yandex.ru/games/sdk/v2`) вообще не загружается, если страница не встроена в
      чужой iframe (`window.self !== window.top`), а не только `YaGames.init()`.
- [ ] `node tools/web_smoke_test.mjs web 8060` проходит без ошибок на локальной сборке.
- [ ] CI-джоб `smoke-test-web` зелёный на следующем пуше.

> ⚠️ Частично реализовано: первая попытка (обернуть только `YaGames.init()` в проверку `window.self !==
> window.top`) снизила число ошибок с 12 до 5, но не убрала целиком — сама библиотека
> `https://yandex.ru/games/sdk/v2` при обычной загрузке через `<script src>` уже пытается достучаться до
> родителя через `postMessage`, независимо от того, вызываем ли мы `init()`. Исправлено: в
> `export_presets.cfg` (`html/head_include` Web-пресета) тег `<script src=...>` заменён на динамическое
> `document.createElement("script")`, добавляемое в `<head>` только внутри `if (window.self !== window.top)`
> — вне iframe скрипт SDK вообще не запрашивается и не выполняется, `window.ysdk` остаётся `null` как и
> раньше в локальном/дебаг-режиме (`core/yandex_sdk.gd` уже обрабатывает `null`, см. ARC-075). На реальной
> площадке Yandex Games поведение не меняется — SDK как загружался, так и загружается, только теперь через
> `s.onload` перед `init()`. Не проверено вживую: нужно пересобрать Web-экспорт и прогнать
> `node tools/web_smoke_test.mjs web 8060` — из сандбокса нет Godot для экспорта.

- [x] Данные события вынесены в `Resource` (`EventData.gd`) по аналогии с картами/артефактами.
- [x] Минимум 5 событий реализовано и подключено к генератору карты.

> ✅ **Реализовано и проверено.** Добавлено:
> - `data/resources/event_data.gd` (`EventData`) — плоский Resource, как `CardData`/`ArtifactData`: `event_title`, `event_description`, `options: Array[Dictionary]`. ### ARC-016 — Колода забега (Run Deck) как отдельная сущность
- **Тип:** Story · **Приоритет:** Blocker (для Эпика B) · **Оценка:** 5 SP
- **GitHub Issue:** [#36](https://github.com/Naraks/arcomage-alfa/issues/36)

**Описание:** Сейчас `MatchManager.deck` — это общий тестовый пул из 11 захардкоженных путей, который
дополняется случайными повторами до 20 карт (`_initialize_test_deck()`). Для роглик-цикла нужна персистентная
колода забега: стартовый набор + карты, добранные в наградах/магазине, которая передаётся между сценой карты и
сценой боя через `MatchSettings`.

**Технические детали:**
- Добавить `MatchSettings.run_deck: Array[CardData]`.
- `match_manager.setup_match()` должен принимать колоду извне вместо вызова `_initialize_test_deck()`, когда
  идёт забег (тестовый режим из главного меню оставить как fallback).
- Просмотр колоды в бою: "рубашка" колоды внизу слева экрана боя (счётчик карт), по клику — попап со всеми
  картами, оставшимися в `MatchManager.deck`.

**Критерии приёмки:**
- [x] Карта, полученная в награде/магазине, действительно доступна в следующем бою этого забега.
- [x] Между боями внутри одного забега колода не сбрасывается.
- [x] В бою внизу слева видна "рубашка" колоды со счётчиком карт; клик открывает список карт в колоде.

> ✅ Реализовано и проверено: `MatchSettings.run_deck: Array[CardData]` — колода забега, персистентна между
> сценами (world_map_screen ↔ battle_screen) как и остальной `MatchSettings`. `match_manager.setup_match()`
> получил третий параметр `p_run_deck` (дефолт `[]`) — если не пуст, `deck` заполняется его ШУФЛ-КОПИЕЙ
> (`p_run_deck.duplicate()`), а не самим массивом: карты, разыгранные/сброшенные за бой, не пропадают из
> забега навсегда, потому что бой работает с копией. При пустом `p_run_deck` поведение не изменилось —
> старый `_initialize_test_deck()` (вынесен общий список путей в константу `STARTER_DECK_CARD_PATHS`, чтобы
> не дублировать его в новом `build_starting_run_deck()`). `main_menu.gd._on_campaign_pressed()` инициализирует
> `MatchSettings.run_deck` стартовой колодой при старте кампании (реальная система разблокировки стартовых
> колод — ARC-038, пока единственный доступный набор); `_on_battle_pressed()` (тестовый бой не из забега)
> явно сбрасывает `run_deck = []`, чтобы колода предыдущей кампании не протекла в тестовый бой.
> `battle_screen._ready()` передаёт `MatchSettings.run_deck` в `setup_match()` третьим аргументом.
> Награды/магазин (ARC-015/ARC-012) ещё не реализованы — добавление карты в `run_deck` из UI руками не
> проверялось, но механизм, которым это будет пользоваться, покрыт тестами напрямую (`tests/test_match_manager.gd`,
> раздел `setup_match / run_deck`): карта, добавленная в `run_deck`, реально оказывается в бою; `run_deck` не
> мутируется/не расходуется вызовом `setup_match()`; без `run_deck` работает старый фоллбэк. (Изначально
> колода была общей на игрока и ИИ — исправлено ниже, см. отдельную `enemy_deck`.)
>
> Добавлен просмотр колоды в бою: `battle_screen.tscn` — `HandArea` перестроен в `HandRow` (`%DeckPileButton`
> слева, `ScrollContainer` с рукой справа, как и раньше). `%DeckPileButton` показывает счётчик
> (`update_all_ui()`), клик открывает попап `_show_card_list_popup()` — полноэкранная затемнённая подложка
> (клик по ней закрывает попап, `Panel` поверх останавливает клики внутри себя) + прокручиваемая сетка карт
> через тот же `entities/card` компонент, что и рука, но без подписки на `card_clicked`/`card_right_clicked` —
> чисто read-only просмотр. Карты в попапе отсортированы по типу ресурса → стоимости → имени
> (`_compare_cards_for_view`), а не показаны в реальном (перемешанном) порядке тяги — так удобнее пробежаться
> глазами, и заодно не "спойлерит" следующую карту. Функция `_show_card_list_popup()` написана как переиспользуемый
> общий попап "список карт", не завязанный только на колоду — пригодится и для будущего просмотра сброса/награды.

> Баг, найденный пользователем при проверке: попап колоды открывался не по центру экрана, а уезжал вправо-вниз.
> Причина — `set_anchors_preset(PRESET_CENTER)` вызывался на только что созданном `Panel` (`.new()`, ещё не в
> дереве сцены), у которого на тот момент `size == (0, 0)`: якорь 0.5/0.5 без явных офсетов превращается не в
> центр попапа, а в его ЛЕВЫЙ ВЕРХНИЙ угол, и попап растёт от центра экрана вправо-вниз, а не вокруг него.

> новому попапу колоды, и к уже существовавшему попапу Victory/Defeat (`_on_match_ended()`) — тот же паттерн
> кода, та же скрытая ошибка, просто ещё не замеченная (300×200 меньше и смещение было не так заметно).

> забега изначально была БЕЗ паддинга (11 карт, "как есть"), а `setup_match()` сразу тянет 10 карт при старте
> боя (5 игроку + 5 ИИ) — от 11 оставалась ровно 1. Следующая же тяга опустошила бы колоду и увела в

> ровно то, что ARC-016 должен был предотвратить. Исправлено: `build_starting_run_deck()` теперь паддит
> колоду случайными повторами до 20 карт, как и тестовая (пока нет реальных наград/магазина — ARC-015/012, —
> которые растили бы колоду органически; когда они появятся, паддинг стоит пересмотреть). Добавлен тест
> `test_build_starting_run_deck_survives_initial_draw`.

> теперь всегда собирает её из общего тестового пула (`_build_generic_card_pool()`, туда же теперь сведены
> `_initialize_test_deck()` и `build_starting_run_deck()`, чтобы не дублировать логику паддинга/шаффла в трёх
> местах), независимо от `run_deck` игрока. `draw_card()` теперь через `_draw_from_deck(is_player)` берёт
> карту из `deck` (игрок) либо `enemy_deck` (ИИ), с тем же поведением "опустел — пересобрать" для каждой
> стороны по отдельности. Добавлены тесты `test_ai_does_not_draw_from_players_run_deck` (карта из `run_deck`
> игрока не может оказаться в руке/колоде ИИ) и `test_setup_match_gives_enemy_independent_deck` (колода ИИ не
> меняется при изменении колоды игрока — независимые массивы, не общая ссылка). Проверено в редакторе: попапы
> центрируются корректно, колода в начале боя не пустеет, ИИ нормально играет карты из своей отдельной колоды.

### ARC-017 — Узел-босс и завершение забега

### ARC-018 — Автосохранение состояния текущего забега

- [x] Состояние забега сохраняется после каждого узла карты.
- [x] При перезапуске игры кнопка «Продолжить» восстанавливает забег с того же места.

> ✅ **Реализовано и проверено.** Добавлены:
> - `data/resources/run_save_data.gd`: `RunSaveData extends Resource` — снимок состояния забега
>   (`world_map_data`, `run_deck`, `run_gold`, `run_tower_bonus`/`run_quarry_bonus`/`run_magic_bonus`/
>   `run_dungeon_bonus`, `run_artifacts`). Прямое зеркало подмножества `MatchSettings`, которое переживает

>   входят — сохранение делается только между узлами, когда боя нет и `current_map_node` уже `null`.

>   `user://run_save.tres`, **не** через JSON (в отличие от `ProfileManager`): состояние забега — граф

>   вложенные под-ресурсы прямо в `run_save.tres` с сохранением разделяемых ссылок между `connected_nodes`, а
>   карты/артефакты (у них `resource_path` уже указывает на `res://data/...`) сохраняются как ссылка на
>   исходный файл, а не дублируются. Ручной JSON-сериализатор графа узлов был бы существенно сложнее ради того

>   `map_data` — единая точка автосохранения вместо дублирования вызова в каждом из 4 screen'ов (shop/rest/
>   event/reward), которые все возвращают на `world_map_screen.tscn` уже проставив `is_completed`/
>   `current_node_index` и сбросив `current_map_node` в `null`. Это же покрывает сохранение сразу после
>   генерации нового забега (первый заход на карту).
> - `ui/main_menu.gd`: `_ready()` дизейблит `ContinueButton`, если `RunSaveManager.has_saved_run()` — false;
>   `_on_continue_pressed()` теперь реально грузит сейв (`RunSaveManager.load_run()`) и переходит на
>   `world_map_screen.tscn` вместо заглушки-принта.
> - `ui/run_summary/run_summary_screen.gd._on_menu_pressed()`: `RunSaveManager.clear_run()` перед выходом в
>   главное меню — это единственная точка выхода после боя с боссом (победа или поражение), т.е. забег
>   гарантированно закончен, и сейв больше не должен предлагаться «Продолжить».
> - Юнит-тесты (GUT, `tests/test_run_save_manager.gd`): `build_save_data()` копирует все поля и делает
>   `duplicate()` массивов (не шарит ссылку с `MatchSettings.run_deck`/`run_artifacts`), `apply_save_data()`
>   раскладывает снимок обратно, round-trip build→apply сохраняет состояние. Реальный файловый I/O
>   (`save_run`/`load_run`/`clear_run`, `ResourceSaver`/`ResourceLoader`/`FileAccess` в `user://`) тестами не
>   покрыт — штатно работает в реальном Godot, но не тестировался в GUT ни для одного из существующих
>   сохранений (`ProfileManager` тоже не тестирует свой файловый I/O, только `add_fame()`), нужна ручная
>   проверка в редакторе.
> - Yandex Player Data (упомянут в описании тикета как следующий шаг) не реализован — это ARC-040, отдельная
>   задача; сейчас сохранение только в `user://`.

### ARC-021 — Расширить интерпретатор эффектов
- **Тип:** Story · **Приоритет:** High · **Оценка:** 5 SP
- **GitHub Issue:** [#41](https://github.com/Naraks/arcomage-alfa/issues/41)

**Описание:** `apply_card_effects()` в `match_manager.gd` поддерживает только `damage`, `direct_damage`,
`build_wall`, `build_tower`, `mod_quarry/magic/dungeon`, `build`. Для карт вида «тянуть карту», «украсть
ресурсы врага», «условный эффект (если X < Y)» нужны новые типы: `draw_card`, `steal_resource`,
`conditional`.

**Критерии приёмки:**
- [x] Добавлены обработчики `draw_card`, `steal_resource`, `conditional` (с вложенным под-эффектом).
- [x] На каждый новый тип эффекта — юнит-тест в `tests/`.

> ✅ **Реализовано и проверено.** `match_manager.gd::apply_card_effects()`
> разобран на `apply_card_effects()` (цикл по `card.effects`) + новую `_apply_effect(effect, actor, enemy)`
> (обработка одного словаря эффекта) — вынесение понадобилось, чтобы `conditional` мог рекурсивно применить
> вложенный под-эффект (`then`/`else`) той же функцией, без дублирования `match`. Добавлены три новых `type`:
> - `draw_card` — `{"type": "draw_card", "target": "self", "value": N}`. `target` резолвится как обычно
>   (`resolve_target`), `value` — сколько раз вызвать уже существующий `MatchManager.draw_card(target_player)`
>   (эта функция была и раньше — её использует раздача стартовой руки в `setup_match()`/`start_turn()`, отдельно
>   писать логику добора не пришлось). Уважает `max_hand_size` (ARC-003) — `draw_card()` сама не тянет сверх
>   лимита.
> - `steal_resource` — `{"type": "steal_resource", "target": "enemy", "resource": "bricks"|"gems"|"beasts",
>   "value": N}`. `target` определяет, **у кого** крадут (резолвится обычным `resolve_target`, обычно `"enemy"`);
>   получает украденное всегда `actor` — это не настраивается через `target` (в отличие от прочих эффектов, здесь
>   участвуют оба игрока сразу, а не один `target_player`). Крадётся `min(value, реально доступно у цели)` — в
>   минус ресурс цели уйти не может.
> - `conditional` — `{"type": "conditional", "target": ..., "field": ..., "op": "<"|"<="|">"|">="|"=="|"!=",
>   "threshold": N, "then": {...}, "else": {...}}`. `field` — одно из `wall_hp`/`tower_hp`/`bricks`/`gems`/
>   `beasts`/`quarry`/`magic`/`dungeon` у `target_player`, резолвленного из `target` условия. Ветка `then`/`else`
>   — обычный словарь эффекта со своим собственным `target` (может отличаться от `target` условия — например,
>   «если твоя Стена < 3 — урони Стену врага»), применяется через ту же `_apply_effect()`. Отсутствующая ветка
>   (нет ключа `then` или `else` в словаре) — просто ничего не делает.
> - `docs/effects_reference.md` дополнен разделами по всем трём типам (справочник — источник истины для
>   контент-авторов, ARC-005).
> - Юнит-тесты (GUT, `tests/test_match_manager.gd`): по 2-3 теста на тип — `draw_card` (пополняет руку target'а,
>   несколько карт по `value`, не превышает `max_hand_size`), `steal_resource` (переносит ресурс от цели к actor'у,
>   клэмпится к реально доступному количеству), `conditional` (ветка `then` при истинном условии, `else` при
>   ложном, вложенный эффект резолвит свой `target` независимо от `target` условия).
> - Сами новые типы эффектов ни в одну `.tres`-карту не добавлены — это по описанию тикета: расширить
>   интерпретатор и покрыть тестами, наполнение контентом (`draw_card`/`steal_resource` в реальных картах вроде
>   «Ясновидение»/«Кража эссенции») — задача ARC-020.

### ARC-023 — Балансировочный проход по стоимости/эффекту карт

- [x] Отчёт по winrate/usage rate каждой карты на выборке ≥500 симулированных боёв.

> применяет бонусы `ProfileManager` только к стороне A, а зеркальные матчапы (`default vs default`,

> агрегации по картам, но абсолютные winrate карт стоит читать с этой поправкой — отчёт остаётся эвристикой

> независимо от cost-тира, тогда как боевые/стеновые карты тяготеют к 50–84% — экономика слишком медленно
> окупается в текущем темпе партий; cost −1 либо value +):

### ARC-084 — Ребаланс экономики: не хватает дорогих карт-«стоков» для ресурсов
- **Тип:** Task · **Приоритет:** High · **Оценка:** 5 SP · **Зависит от:** ARC-023, ARC-054
- **GitHub Issue:** [#85](https://github.com/Naraks/arcomage-alfa/issues/85)

**Описание:** Со слов автора после игровых сессий: ресурсы (Кирпичи/Гемы/Звери) копятся намного быстрее, чем
находится, на что их потратить — в руке (5 карт максимум) почти всегда лежат только дешёвые варианты, крупный
запас ресурсов простаивает без применения. Распределение `cost` по всем ~65 картам (после нерфов ARC-023,
максимум сейчас `cost=8`) сильно смещено к дешёвому концу: `cost` 1–3 — 42 карты (~65%), `cost` 5 и выше —
всего 14 карт (~21%), из них `cost` 7–8 — только 4 карты на весь пул. Реальный импакт (урон/рост
башни/генераторов) при этом растёт медленнее, чем должен бы расти вместе с ценой, поэтому нет ощущения «коплю
на что-то по-настоящему сильное» — сильные карты просто оказываются чуть дороже слабых, а не качественно
другим уровнем воздействия. Нужно осознанно развести дешёвый и дорогой сегменты: у дорогих карт impact/cost
должен расти нелинейно (дороже карта — тем большую отдачу с каждой единицы cost она даёт, а не такую же или
меньшую), чтобы решение «копить 5–6 ходов ради одной карты» было явно выгоднее, чем сразу тратить ресурсы на
россыпь дешёвых.

**Критерии приёмки:**
- [ ] Аудит текущего пула: для каждой карты посчитано отношение impact/cost (урон, прирост генератора, прирост
      стены/башни на единицу `cost`); задокументировано в `docs/cards_list.md` или отдельной таблице, показана
      кривая роста impact/cost по возрастанию `cost` — должна быть заметно растущей у дорогих карт, не плоской.
- [ ] Либо добавлены новые карты-«бомбы»/«стоки» с `cost` заметно выше текущего максимума (9+), либо
      пересмотрен impact существующих дорогих карт (5+) в сторону непропорционально большего эффекта — так,
      чтобы у игрока появился явный резон копить несколько ходов, а не разыгрывать ресурсы по мере поступления.
- [ ] Пересмотрена скорость притока ресурсов (базовые генераторы `quarry`/`magic`/`dungeon`, стартовые запасы в
      `PlayerData`, сила карт-генераторов) — если профилирование покажет, что приток кардинально опережает
      трату даже после добавления дорогих карт, снизить его, а не только наращивать сток.
- [ ] Повторный прогон `tools/battle_simulator.gd` (ARC-054) на обновлённом балансе; в отчёт добавлена метрика
      среднего «простаивающего» остатка ресурсов на конец партии (или на момент виктории) — до/после правки, с
      цифрами в блокквоте тикета.

### ARC-029 — Масштабирование сложности по этажам карты

### ARC-030 — Триггер `on_damage_taken` в системе артефактов
- **Тип:** Task · **Приоритет:** High · **Оценка:** 3 SP · **Зависит от:** ARC-004
- **GitHub Issue:** [#50](https://github.com/Naraks/arcomage-alfa/issues/50)

**Описание:** `artifact_manager.gd` сейчас реагирует только на `card_played` и `turn_started`. Для «Шипастой
Стены» (урон в ответ при попадании по стене) и подобных артефактов нужен триггер на входящий урон.

**Критерии приёмки:**
- [x] `ArtifactManager` подписан на новый сигнал урона (после ARC-004) и вызывает эффекты с `trigger = "on_damage_taken"`.

> ✅ **Реализовано и проверено.** `ArtifactManager` уже
> был подключён в реальной игре — но не как autoload, а как child-нода, создаваемая вручную в
> `MatchManager._ready()` (`artifact_manager = load(...).new(); add_child(artifact_manager)`); раз `MatchManager`
> сам autoload, этот паттерн тоже работал (child получает `_ready()` сразу при `add_child()`), просто был не
> нужен как отдельный публичный синглтон. Понадобился настоящий autoload из-за ARC-035: `MatchManager.
> play_card_by_index()` должен СИНХРОННО спросить `ArtifactManager.should_skip_payment()` до списания
> ресурсов — с ArtifactManager как приватной child-нодой внутри самого MatchManager (без публичного имени)
> это было бы циклической зависимостью на самого себя, а не чистым вызовом одного автозагруза из другого.
> Сделал `ArtifactManager` полноценным autoload (`project.godot`), `class_name ArtifactManager` убрал —
> конфликтует с именем автозагрузки, тот же паттерн, что у
> MatchManager/GameEvents/MatchSettings/ProfileManager/RunSaveManager (ни один не объявляет class_name), и
> **убрал старую child-инициализацию из `MatchManager._ready()`** — иначе получились бы ДВА живых экземпляра
> `ArtifactManager`, оба подписанные на одни и те же `GameEvents`, и каждый эффект срабатывал бы дважды
> (это поймал самопроверочный агент до коммита, не runtime — см. ниже). `tests/test_artifact_manager.gd`
> переведён на прямое обращение к синглтону (как `tests/test_match_manager.gd` к `MatchManager`), а не
> создание отдельных экземпляров.
>
> Сам триггер: `GameEvents.damage_applied` получил 4-й параметр `source: Resource` (кто нанёс урон — сигналы
> GDScript не поддерживают значения по умолчанию, `null` проставляет сам `MatchManager.apply_damage()`, если
> вызван без `source`; существующие подписчики с меньшим числом параметров, напр. `battle_screen.gd`, не
> ломаются — Godot допускает подключать `Callable` с меньшей арностью, чем у сигнала).
> `MatchManager.apply_damage()` получил параметр `source: PlayerData = null`, оба реальных вызова (`damage`/
> `direct_damage` в `_apply_effect()`) передают `actor`. `ArtifactManager._on_damage_taken()` подписан на
> `damage_applied`, приводит `target` к `PlayerData` и вызывает `_check_artifacts(target, "on_damage_taken",
> {"amount":.., "hit_wall":.., "attacker": source})` — `_check_artifacts()`/`apply_artifact_effect()` заодно
> получили общий параметр `context: Dictionary` (нужен не только этому триггеру, но и `card_played` для
> ARC-032, см. там).

### ARC-031 — Артефакт «Шипастая Стена»
- **Тип:** Story · **Приоритет:** Medium · **Оценка:** 2 SP · **Зависит от:** ARC-030
- **GitHub Issue:** [#51](https://github.com/Naraks/arcomage-alfa/issues/51)

- [x] При ударе по стене владельца артефакта атакующий получает 2 урона.

> ✅ **Реализовано и проверено.** `data/artifacts/spiky_wall.tres` — эффект
> `{"trigger": "on_damage_taken", "type": "reflect_damage", "value": 2}`. Новый тип `reflect_damage` в
> `apply_artifact_effect()`: срабатывает только если `context.hit_wall` истинно (не на `direct_damage` мимо

> - `ignore_wall=true` (как у `direct_damage`) — ответный удар "шипов" не гасится стеной самого атакующего.

> - Защита от бесконечного пинг-понга: если у ОБЕИХ сторон стоит Шипастая Стена, `_reflecting` (флаг в
>   `ArtifactManager`) не даёт отражённому удару самому переотразиться — иначе урон бы летал туда-сюда
>   бесконечно (пока стены не обнулятся). Проверено юнит-тестом
>   `test_reflect_damage_does_not_infinite_loop_when_both_sides_have_the_artifact`.
>
> Тесты: `tests/test_artifact_manager.gd` (прямые вызовы `_on_damage_taken()`) и интеграционный
> `tests/test_match_manager.gd::test_play_card_by_index_damage_triggers_reflect_damage_artifact_on_defender`

> превращался в `2.0`; строгое сравнение словарей (тест, GUT) видело в этом разницу, хотя по значению это
> одно и то же число. Затрагивало не только новый `upgrades` — `fame`/`total_wins` страдали тем же молча (не
> ловилось раньше просто потому, что раньше никто не сравнивал их через `assert_eq` именно после полного
> save→load цикла). Добавил `_restore_int_types()` — рекурсивно приводит float без дробной части к int по
> всему дереву `Dictionary`/`Array` при загрузке. Осознанное допущение: в `profile` нет полей, которым
> намеренно нужна дробная точность (все — счётчики/уровни/валюта), так что цена (гипотетическая потеря
> reального `2.0`) отсутствует на практике.

### ARC-054 — Симулятор «ИИ против ИИ» для баланса
- **Тип:** Story · **Приоритет:** High · **Оценка:** 8 SP · **Зависит от:** ARC-025, ARC-026
- **GitHub Issue:** [#74](https://github.com/Naraks/arcomage-alfa/issues/74)

**Описание:** Прямое требование матрицы рисков («Автоматические тесты боя ИИ против
ИИ для сбора статистики»), которое пока не реализовано. Запуск сотен автобоёв в headless-режиме
(`godot --headless`) с логированием победителя, длительности, использованных карт.

**Критерии приёмки:**
- [x] Скрипт прогоняет N боёв между произвольными комбинациями стратегий и пишет CSV/JSON отчёт.
- [x] Отчёт используется в ARC-023 для баланса карт.

> ✅ **Реализовано и проверено.** Первая версия была `SceneTree`-скриптом, запускаемым через `-s` (как GUT) —
> при реальном запуске (уже локально, автором тикета) это дало `Compile Error: Identifier not found:
> GameEvents` на `res://tools/battle_simulator.gd:69`. Причина: скрипт, переданный движку через `-s`,
> компилируется **до** регистрации автозагрузок как глобальных идентификаторов — в отличие от
> `addons/gut/gut_cmdln.gd`, который сам никогда не трогает автозагрузки проекта напрямую (только `load()`-ит
> свои же addon-файлы, и уже они, скомпилированные позже как обычные `Node`-скрипты, свободно используют
> `MatchManager`/`GameEvents`). Исправлено: `tools/battle_simulator.gd` теперь `extends Node` (не `SceneTree`),
> вход через `_ready()` (не `_init()`), запускается как обычная сцена `tools/battle_simulator.tscn`, явно
> указанная позиционным аргументом (это подменяет main scene только для этого запуска):
> `godot --headless --path . res://tools/battle_simulator.tscn -- --games=500 --out=balance_report.csv`.
> Обычная сцена компилируется уже после полного бутстрапа автозагрузок — `GameEvents`/`MatchManager` доступны
> как везде в проекте. Каждая игра — независимый бой через `MatchManager` (тот же автозагруз,
> что использует `battle_screen.gd`/GUT-тесты) между двумя случайно выбранными стратегиями из
> Default/Aggressive/Builder/Economist (ARC-025/026). Обе стороны ведёт новая `MatchManager._resolve_ai_turn
> (actor)` — рефакторинг `execute_ai_turn()`: секундная задержка "для комфорта игрока" вынесена в саму
> `execute_ai_turn()` (`await create_timer(1.0).timeout` → вызов `_resolve_ai_turn(enemy_data)`), а чистая
> логика хода обобщена на любого `actor` и переиспользуется симулятором без await — иначе 500 игр реально шли
> бы часами. Пишет два CSV: по картам (`card_name,times_played,times_on_winning_side,win_rate_when_played`,
> предзаполнен нулями для ВСЕХ карт `MatchManager.ALL_CARD_PATHS`, чтобы никогда не разыгранные карты не
> выпадали из отчёта) и по матчапам стратегий (`<out>_matchups.csv`).
>
> **Важная техническая деталь**: `setup_match(p_run_deck=...)` даёт полный 66-карточный пул только стороне A
> (`player_data`) — для стороны B (`enemy_data`) в API нет параметра, её колода всегда строится из
> `STARTER_DECK_CARD_PATHS` (11 карт). Без переопределения `enemy_deck`/`enemy_hand` сразу после `setup_match()`
> сторона B никогда не видела бы 55 из 66 карт — отчёт был бы бессмысленным для всего контента ARC-019/020.
> Симулятор это переопределяет явно (задокументировано в самом скрипте).
>
> Реальный запуск подтверждён: `--games=500` на машине пользователя после фикса дал ровно 500 игр без ошибок,
> два CSV (`balance_report.csv`, `balance_report_matchups.csv`) присланы и использованы для правок баланса в
> ARC-023 — второй акцептанс-критерий тем самым выполнен фактически, не только на бумаге.
>
> CI **не** запускает симулятор автоматически (в отличие от GUT-тестов/coverage-report) — 500 игр было бы
> заметной нагрузкой на каждый push/PR ради статистики, которая нужна не на каждый коммит, а периодически для
> баланс-прохода (ARC-023). Инструмент — как `tools/coverage_report.py`, вызывается вручную по мере надобности,
> не часть обязательной проверки.
>
> Юнит-тестами покрыт только сам рефакторинг `_resolve_ai_turn()` (обобщение на любого `actor`, не только
> `enemy_data`) в `tests/test_match_manager.gd` — это то, что GUT реально может проверить в этой среде;
> сам батч-скрипт `battle_simulator.gd` GUT не запускает (другой режим исполнения Godot, обычная сцена вместо
> тестраннера).
